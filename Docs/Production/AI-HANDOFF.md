# AI 全栈生产交接协议

## 目标与完成边界

本仓库的目标是支撑中型、内容驱动的视觉小说/卡牌等单机游戏生产。工作流可用不等于样例游戏功能齐全；样例通关也不证明美术、音频、叙事规模化生产、性能和发行链路已就绪。容量数字沿用 `Docs/ROADMAP.md` 的待确认包络，不新增发行承诺。

## 单项任务契约

跨工种任务使用 `.github/ISSUE_TEMPLATE/production.yml`，本地工作也填写同等字段。开始执行前必须具备目标、非目标、权威输入、允许修改范围、负责人、验收 ID、验证方法、候选交接与回滚。缺失时先补规格；AI 可以起草，不能冒充负责人批准主观决策。

交接顺序：权威输入 → 隔离候选 → 自动验证 → 人工评审 → 集成预览 → 回归/构建 → 证据交付。失败返回产生问题的阶段；不得用自动分数替代审美、叙事、许可或发行判断。

## 工种交接最小要求

| 工种 | 候选输入/输出 | 自动检查与人工证据 | 下游 |
| --- | --- | --- | --- |
| 设计/数值 | RFC、稳定 ID、版本化规则内容 | schema、引用、固定策略/种子报告；设计确认 | Gameplay、QA |
| 叙事/本地化 | 分支、变量、条件、文本 key、语言目录 | 可达性/条件测试、覆盖；分支通读与语言审校 | UI、QA |
| 美术/动画 | 批准方向、来源许可、源文件、导出资产 | 导入/引用/预算检查；目标分辨率实机画面评审 | Presentation |
| 音频 | 批准声音方向、许可、源文件、事件映射 | 导入/引用/包体检查；实际播放、循环与混音评审 | Presentation |
| 工程/工具 | RFC/ADR、契约、源代码、失败用例 | EditMode/PlayMode、完整 Workflow、Player 构建 | 集成、QA |
| QA/性能 | 内容版本、硬件、种子、复现步骤 | 测试报告、Profiler 捕获、人工兼容矩阵 | 修复任务、负责人 |
| 构建/发行 | 不可变制品、manifest、批准记录 | 干净安装、旧档、离线/平台、回滚演练 | 授权发布 |

以上是交接要求，不表示各行已有自动实现。当前结构化内容候选工具不覆盖图像、音频或第三方许可鉴定；这些工种需保存人工证据，不能复用 JSON 报告冒充视听验收。

## 证据规则

- 每项 AC 必须记录输入版本、执行命令/人工步骤、日期、结果和证据路径；结论区分事实、推断、未验证。
- 内容审阅沿用 RFC-008：隔离 draft、来源记录、SHA-256 绑定、独立人工批准、原子晋级。不得直接改 approved 数据来绕过审批。
- 策略对照固定内容与种子，记录策略版本；若修改策略或数值，旧胜率不是可直接比较的基线。
- CI 配置文件只证明配置存在，不证明远端运行成功；本地构建不证明 Steam 发布或干净安装成功。
- 一个未完成的必要验收项就足以保持任务未完成；可交付阶段成果，但必须列出剩余项。

叙事导入与候选审阅还会执行 RFC-011 拓扑检查：入口为声明的 startNodeId 与所有 Story 路线入口，检查不可达节点及没有终止路径的节点。允许有出口的循环；条件边仅按潜在可走路径计算，因此通过不代表变量条件可满足。遇到稳定 ID 错误应修复作者源，不要自动删除分支或伪造入口。

## 本地证据完整性检查

运行 `pwsh Tools/Test-TaskEvidence.ps1 -Specification <spec.json> -Evidence <evidence.json>`。检查器只读文件，不执行 `method` 中的命令、不发布、不晋级内容。规格必须来自已审阅的任务卡；修改规格和证据即可伪造自洽记录，因此该工具不是审批认证或防篡改安全边界。

规格 v1 示例：

```json
{"schemaVersion":1,"taskId":"task.example","inputVersion":"content.example.1","owner":"responsible-human","acceptanceIds":["AC-01"],"requiresHumanApproval":true}
```

证据 v1 包含相同的 `taskId/inputVersion/owner`，以及 `results` 数组。每项必须有 `id`、`status`（完成检查只接受 `passed`）、`method`（实际命令或人工协议）、`verifiedAtUtc`（UTC Z 时间）和非空 `artifacts`。每个 artifact 提供仓库相对 `path` 与 64 位十六进制 `sha256`。哈希可用 `Get-FileHash -Algorithm SHA256` 获取。路径不得越界或经过链接；文件缺失或内容变化均拒绝。

需要人工批准时，另有 `approval` 对象：`status`、`reviewer`、`reference`。真实审核人必须提供批准记录；AI 不得为通过检查填写虚假身份。工具只检查这些字段存在与状态，审核人身份、证据语义、规格完整性、输入来源和审批真实性仍必须人工确认。

验收：每个规格 AC 恰有一个通过结果；版本与负责人一致；证据存在且哈希匹配；未验证/待批准记录被拒绝。`pwsh Tools/Test-TaskEvidence.Tests.ps1` 覆盖有效合成夹具及九类失败，已接入 Workflow。测试中的 synthetic reviewer 不是实际批准记录。

回滚：移除两个 `Test-TaskEvidence` 脚本、Workflow 中测试调用和本节；不修改运行时或存档。

## 生产能力演练（执行要求）

在扩大内容数量前，由非程序负责人发起一张卡、一个敌人、一个叙事分支以及一组视听资产的代表性任务，走完以上交接。记录实际工时、返工次数、失败原因和审核人，用实测吞吐量修订容量预算。演练未执行前不得将阶段标记为生产就绪。

## 本协议验收与回滚

检查任务表单覆盖七类工种和契约字段，PR 表单能逐 AC 记录证据与待审批事项，链接的现有脚本/规范存在。GitHub 在线表单渲染需远端人工确认。此变更不改运行时、数值或存档；回滚撤回新增表单/本文和相关入口修改即可。
